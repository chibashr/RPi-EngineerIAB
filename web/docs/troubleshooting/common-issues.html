Common issues

Start here when the web interface is slow or the device behaves unexpectedly.

Web interface not loading

Symptom: Browser cannot reach http://192.168.50.1.

Common causes: Not connected to WiFi hotspot, device still booting.

Resolution: Reconnect to the hotspot and wait two minutes for full boot.

403 Forbidden when opening 192.168.50.1

Symptom: Browser shows 403 Forbidden when opening http://192.168.50.1 (e.g. from hotspot or LAN). Nginx error log may show directory index of "/opt/rpi-engineer/web/" is forbidden.

Common causes: (1) Nginx access rules blocking LAN/hotspot. (2) Web root or index.html not readable by nginx—nginx runs as www-data (or the user in /etc/nginx/nginx.conf); if it cannot read the web root or the index file, you get 403.

Resolution: Run the bundled fix once (as root): sudo /opt/rpi-engineer/bin/apply-web-permissions.sh. It rewrites the nginx config and sets web root ownership so the UI is reachable.

If that script is missing (e.g. command not found or incomplete install), fix it manually on the device (as root):

  1. Ensure nginx can read the web root and traverse to it: 
    chown -R www-data:www-data /opt/rpi-engineer/web
chmod o+x /opt /opt/rpi-engineer
  2. Ensure the site config uses root /opt/rpi-engineer/web; and index index.html; and allows access (e.g. allow all; in the server block). Edit /etc/nginx/sites-available/rpi-engineer if needed.
  3. Test and reload nginx: 
    nginx -t && systemctl reload nginx

If index.html is missing under /opt/rpi-engineer/web/, re-deploy the web folder from the repo or re-run the full installer. To confirm the cause, check /var/log/nginx/error.log (e.g. Permission denied or 13 means file permissions).

Permission denied: /var/lib/rpi-engineer/updates/state.json

Symptom: Update fails with [Errno 13] Permission denied: '/var/lib/rpi-engineer/updates/state.json'.

Cause: The API user cannot create or write the update state file under the data directory (e.g. directory missing or wrong ownership in a container).

Resolution: (1) On a normal install, re-run the installer so it creates data/updates and data/staging and sets ownership to root:SERVICE_GROUP with dirs 775. (2) The app tries fallbacks when the primary path is not writable: first repo/data/updates/state.json, then the process temp dir (e.g. $TMPDIR/rpi-engineer-updates/state.json). If both data dirs are read-only (e.g. container), state is written to temp so updates can proceed; set RPI_ENGINEER_DATA_DIR to a writable directory if you prefer persistent state.

Permission denied when applying update

Symptom: Clicking Update (keep configuration) shows an error such as [Errno 13] Permission denied: '/etc/rpi-engineer/remote_access.conf'.

Cause: The pre-update config backup runs as the API user and cannot read root-owned config files (e.g. remote_access.conf).

Resolution: Re-run the installer so it can add the sudoers rule for create-config-backup.sh (the service user can then run that script as root with NOPASSWD to create the backup). From the repo: sudo ./bin/install.sh, choose Upgrade and use existing configuration. If you already ran the installer after this fix was added, the in-app update should work without a password.

Update failed: "dubious ownership" in repository

Symptom: Update fails with fatal: detected dubious ownership in repository at '/opt/rpi-engineer' and suggests git config --global --add safe.directory /opt/rpi-engineer.

Cause: Git 2.35.2+ refuses to use a repo when the current user does not own the directory (e.g. API runs as rpi-engineer, repo is root:rpi-engineer).

Resolution: The app and installer now add safe.directory for the install path. Re-run the installer so it runs git config --system --add safe.directory /opt/rpi-engineer. Or run that command once as root. After that, in-app update should work without the error.

Update failed: "no new privileges" or sudo blocked in container

Symptom: Applying an update shows Update failed; rollback attempted: sudo: The "no new privileges" flag is set... or similar.

Cause: The app is running in a container (or environment) where sudo cannot elevate to root (e.g. no_new_privs or restricted capabilities).

Resolution: The update logic now falls back to running git fetch and git reset --hard in-process when sudo fails with this error, so the update can complete without root. Ensure the repo directory (e.g. /opt/rpi-engineer) is writable by the API user. If you need apply-update.sh or web-permissions logic to run as root, run the container without the no-new-privileges flag or adjust the container configuration so sudo can run.

Update failed: cannot open '.git/FETCH_HEAD': Permission denied

Symptom: Update runs without sudo (e.g. in a container) then fails with error: cannot open '.git/FETCH_HEAD': Permission denied. The UI may show a clearer message: "Repository directory is not writable by this user…". If rollback runs, it now skips config files it cannot write and restores the version to data/version when config/version is not writable, so "Rollback failed" with permission denied on config is less common.

Cause: The install directory is owned by root and the API user cannot write to .git/, so git fetch fails.

Resolution: (1) Prefer running updates as root: ensure sudo can run bin/apply-update.sh (installer adds a sudoers rule). (2) If running without sudo (e.g. container), make the repo writable by the API user: as root, chmod -R g+w /opt/rpi-engineer/.git and ensure the API user is in the group that owns the install dir. Or install to a directory owned by the service user so in-process git fetch can write to .git.

Why did it say "rollback attempted"?

Symptom: You clicked Update and see Update failed; rollback attempted: <some error>. You only wanted to update, not roll back.

Explanation: When the apply step fails (e.g. git error, permission error), the app automatically tries to roll back to the previous version and config so the device is left in a known state. The message means: "The update failed because of <error>; we then attempted a rollback." If rollback succeeds, you are back at the version you had before clicking Update. Fix the underlying error (e.g. dubious ownership, permission denied) and try Update again.

"Update stream connection error" when clicking Update

Symptom: You see a red toast Update stream connection error and the update log shows "Stream connection error. Falling back to REST...".

Cause: The live-update WebSocket (/ws/updates/apply) could not be established (e.g. proxy not upgrading WebSockets, or API not reachable on the WebSocket path).

Resolution: The UI now automatically falls back to the REST apply endpoint, so the update still runs and you should see "Applying update via REST..." then success or an error in the log. If the update then succeeds, no further action is needed. To get the live streaming log, ensure nginx (or your proxy) is configured to upgrade WebSocket for /ws/ and the API is listening; the installer configures this by default.

Updates apply but nothing changes

Symptom: You click Update (keep configuration) and receive a success message, but new UI or code changes never appear.

Common cause: The API is running with RPI_ENGINEER_DRY_RUN=1, which skips applying updates.

Resolution: Ensure the API systemd unit includes Environment=RPI_ENGINEER_DRY_RUN=0 and Environment=RPI_ENGINEER_ROOT=/opt/rpi-engineer. The installer writes these automatically; re-run the installer or update the unit and restart rpi-engineer-api.

No network access

Symptom: WAN shows disconnected on the dashboard.

Common causes: Ethernet unplugged or USB modem not detected.

Resolution: Reseat cables, confirm link lights, and retry.

High temperature warning

Symptom: Temperature alert or degraded status.

Common causes: Poor ventilation or high workload.

Resolution: Improve airflow and pause heavy captures.

Dashboard shows services as stopped but systemctl says running

Symptom: Service Status on the dashboard shows some services as stopped while systemctl status rpi-engineer lists them as active.

Cause: The dashboard reads state from systemd via systemctl show --property=ActiveState --value <unit>. If the API cannot query systemd (e.g. different user context or timeout), or if units were briefly inactive when the check ran, the display can disagree.

Resolution: On the device, verify each unit’s state with systemctl is-active rpi-engineer-api (and similarly for rpi-engineer-system, rpi-engineer-serial, rpi-engineer-logging, rpi-engineer-update, etc.). If they report active, refresh the dashboard or wait for the next poll/WebSocket update. If the mismatch persists, ensure the API service runs with access to systemd (e.g. not in a restricted container that cannot see system units).

TeamViewer running but connection ID not on dashboard

Symptom: systemctl status teamviewerd shows active (running), but the dashboard shows no TeamViewer connection or an empty ID.

Cause: The dashboard gets the ID from the API, which tries: teamviewer info (CLI), then /etc/rpi-engineer/remote_access.conf, then TeamViewer config files (/opt/teamviewer/config/global.conf or /etc/teamviewer/global.conf). If the ID was not yet available at install time or the API user cannot run the CLI or read the config, the field stays empty.

Resolution:

  1. On the device, get the ID: sudo teamviewer info (look for TeamViewer ID:).
  2. If you have a TeamViewer ID, add it to the app config so the dashboard shows it. As root: open /etc/rpi-engineer/remote_access.conf, ensure the teamviewer object has "id": "XXXXXXXXX" (digits only, no spaces). Keep the JSON valid. Save and refresh the dashboard.
  3. Optional: so the API can read the ID from TeamViewer’s config, allow read access: sudo chmod 644 /etc/teamviewer/global.conf (if that file exists). Then restart the API: sudo systemctl restart rpi-engineer-api.

AnyDesk: "Session closed" / "display_server_not_supported"

Symptom: Connecting with AnyDesk using the ID from the dashboard shows a dialog: Session Closed, Status: display_server_not_supported.

Cause: AnyDesk on Linux requires an active graphical display (X11). On headless or console-only systems (no monitor, no desktop session), there is no display server for AnyDesk to attach to, so the connection fails with this error.

Resolution:

  • Use TeamViewer or VNC instead for headless/field devices. TeamViewer and VNC can work in unattended mode without a physical display.
  • If you must use AnyDesk: attach a monitor (or a headless HDMI dongle) and ensure a user is logged in to an X11 desktop session; or use a different machine that has an active display.
